# ВК-мессенджер (vk.com / vk.ru): сообщения, диалоги, выгрузка данных

<!-- sites: vk.com, vk.ru, m.vk.com -->

> Проверено в живой работе: поиск людей, диалоги, отправка сообщений, чтение истории, анализ
> переписок, выгрузка списка диалогов запросом (replay). Версия клиента, селекторы и кнопка
> отправки — из живого замера, а не из памяти модели.
>
> **Главное, на чём спотыкались:** отправку сообщения делают ровно ЧЕТЫРЬМЯ шагами с кнопкой
> отправки. `submit: true`, `browserPress Enter` и `browserAct` в ВК **не отправляют** сообщение —
> они делают вид, что отправили. Подробно — раздел 3.

## 0. Правило нуля: сначала проверить сессию

**Перед любым действием в ВК — `browserText` и убедиться, что сессия жива.** Вкладки ВК умеют
сбрасываться на логин между вызовами, и тогда все дальнейшие шаги уходят в форму входа.

- Открылась страница логина → **сначала менеджер паролей**: `vaultList`, затем
  `vaultFill` (пароль для `vk.com` из секретов приложения).
- Пароля там нет → **попроси человека ввести его в окне браузера самому**. Пароли в чате не
  спрашивают и не придумывают; QR/2FA дожимает человек в открытом окне.
- Работай в **существующей** вкладке: новые вкладки открываются БЕЗ сессии. Закрывай только
  конкретный `tabId`, не «все».

## 1. Адреса (проверены)

| Действие | URL |
|---|---|
| Диалог по ID | `https://vk.com/im/convo/PEER_ID` (пример: `143668553`) |
| Список диалогов | `https://vk.ru/im` / `https://vk.com/im` |
| Поиск людей | `https://vk.com/search?c[section]=people&c[q]=ИМЯ+ФАМИЛИЯ` |
| Профиль по короткому имени | `https://vk.com/<shortname>` (например `jekochka19`) |
| Лента / настройки | `https://vk.com/feed`, `https://vk.com/settings` |

`vk.ru` и `vk.com` взаимозаменяемы. Иногда редиректит на `al_im.php` — это внутренний AJAX-роутинг
ВК: подождать 2–5 сек и перечитать страницу.

## 2. Селекторы (проверены на практике)

| Что | Селектор | Замечание |
|---|---|---|
| Поле ввода сообщения | `[role=textbox]` | = `.ComposerInput__input.ConvoComposer__input`, это `contenteditable`, **НЕ `<input>`/`<textarea>`** |
| Кнопка отправки | `.ConvoComposer__sendButton--submit` | класс стабильный, проверен |
| Строки списка диалогов | `.convo-item` | контейнер — `ConvoList__itemsWrapper` |
| Поле ввода (проверка) | `.ComposerInput__input` | `textContent.length == 0` = поле пустое = отправлено |

`#im_dialogs` и `.nim-dialog` в текущем DOM **не существуют** — не искать их. Поле сообщений —
только `[role=textbox]`, `textarea`-селекторы в ВК для сообщений не работают.

## 3. Отправить сообщение — ровно 4 шага, без отступлений

```
1. browserOpen   { url: "https://vk.com/im/convo/PEER_ID" }
2. browserFill   { selector: "[role=textbox]", text: "текст" }
   → БЕЗ submit: true! Он в ВК не срабатывает.
3. browserClick  { selector: ".ConvoComposer__sendButton--submit" }
4. Проверка: browserEval → document.querySelector('.ComposerInput__input').textContent.length
   → 0 = отправлено ✅
```

Перед шагом 2 убедись, что диалог открыт (`browserText`, 2–5 сек после открытия; если видно
«Загружается…» — подожди и перечитай). После клика по кнопке подожди 1–2 сек и только потом
проверяй поле.

### Чего НЕ делать (это уже стоило времени)

| Нельзя | Что происходит |
|---|---|
| `browserFill { submit: true }` | Ложное «отправлено»: текст залипает в поле и никуда не уходит |
| `browserPress { key: "Enter" }` | В `contenteditable` ВК это перенос строки, а не отправка |
| `browserAct` (пакет click+fill) | Ломается на `contenteditable`: клик «съедает» фокус, текст теряется |
| Искать кнопку по тексту «Отправить» в `browserSnapshot` | Подписи может не быть в карте, а селектор кнопки стабилен: `.ConvoComposer__sendButton--submit` |

## 4. Как подтверждать отправку

Подтверждение — **пустое поле ввода** (шаг 4 выше). История переписки справа тоже
виртуализирована: **«сообщения нет в DOM» ≠ «не отправлено»** — оно может быть просто не
отрисовано. Отправку скроллом истории не подтверждают.

Если поле не опустело — повтори шаги 2–3 (иногда нужен повторный клик по полю перед вводом).

## 5. Виртуализация — два места, о которых надо знать

- **Список диалогов (слева).** Контейнер `ConvoList__itemsWrapper` (`scrollHeight >> clientHeight`),
  строки `.convo-item`. В DOM одновременно ~11–15 элементов, остальные подгружаются прокруткой.
  Старый контакт «пропадает» из списка не потому, что удалён, а потому что не догружен.
  Догрузить и прочитать: `browserScroll { loadAll: true, container: ".ConvoList__itemsWrapper",
  item: ".convo-item" }`, затем `browserSnapshot`/`browserText`. Ещё быстрее — выгрузка запросом
  (раздел 6).
- **История переписки (справа).** Тоже виртуальная; старые сообщения не в DOM, пока не догружены.
  Не листать по одному экрану: `browserScroll { loadAll: true, how: "up", read: true }` крутит,
  пока подгружается, и сразу отдаёт текст. Стикеры и картинки текстом не приходят — только
  скриншотом. Полнее и быстрее — replay `messages.getHistory` (раздел 6).

## 6. Выгрузка списка диалогов и истории: replay запроса клиента

**Суть:** список и история НЕ читаются из DOM надёжно (виртуализация переиспользует узлы, `ref`
устаревают). Зато веб-клиент САМ ходит за этими данными запросом — повторяем ЕГО запрос из самой
страницы (куки и CORS такие же) и листаем ответ курсором.

| Параметр | Факт (живой замер) |
|---|---|
| Эндпоинт списка | `POST https://api.vk.ru/method/messages.getItems` |
| Версия | `v=5.285` — ВНУТРЕННЯЯ версия клиента: брать ТОЛЬКО из перехвата (свои 5.95/599 сервер отвергает ошибкой 100 `invalid v`) |
| Тело | `start_from=conversations_<id>&filter=all&target_count=20&extended=1&access_token=…` — токен в ТЕЛЕ (form-encoded), не в query |
| Ответ | `response.conversations.items[]` + `total_count`, курсор — `last_item` |
| Следующая страница | `start_from=conversations_<last_item>` |
| Конец | `items.length == 0` ИЛИ собрано `total_count` |

Порядок (2–3 вызова вместо 7–8 ходов «прокрутил → снял карту»):

```
1. browserOpen("https://vk.com/im")            — клиент сам делает первый запрос списка
2. browserNetwork { since: false, filter: "messages.getItems" }
   — берём адрес (там v=5.285) и тело (там токен, секреты скрыты)
3. browserReplay { match: "messages.getItems", cursorParam: "start_from",
                   cursorPrefix: "conversations_", maxSteps: 40 }
   — повторяет тот запрос ИЗ СТРАНИЦЫ, листает курсором, кладёт items[] в ФАЙЛ
4. readFile(path из ответа) — разбор своим кодом (или pick-поля в самом вызове)
```

История диалога — та же схема: открыть `vk.ru/im/convo/<peer_id>`, догрузить вверх, затем
`browserReplay { match: "messages.getHistory" }` с `cursorParam` из перехвата.

Грабли replay:

- **Не подставляй `v` руками** — это полчаса на ошибку 100 `invalid v`. Версия и токен берутся из
  перехвата.
- **Токен не «вытаскивай»** в текст: replay повторяет запрос внутри страницы, где сессия на месте.
  `credentials: 'include'` тащит куки сам.
- **Пагинация курсорная** (`start_from=conversations_<id>`), а не `offset`.
- **Накопленное — в файл** (`save: true` у `browserReplay`/`browserEval`), а не в `window.__var`:
  перезагрузка вкладки стирает переменные, файл остаётся.
- Replay отказал (CSRF/изменился запрос) — fallback: прокрутка `ConvoList__itemsWrapper` +
  `browserNetwork`.

## 7. Подводные камни и баги инструментов

| Баг инструмента | Обход |
|---|---|
| `browserEval` с IIFE `(function(){…})()` не возвращает значение | Либо простое выражение, либо `window.__x = …` и отдельный вызов `window.__x` |
| `browserNetwork` показывает поллинг ВК (`a_check`, `queuev4`) и засоряет журнал | `filter: "messages.getItems"`; либо `browserNetwork { clear: true }` перед триггером |
| Страница ВК перезагружается между вызовами → `window.__var` теряется | Сохранять в файл (`save: true`), не в `window` |
| Вкладки ВК сбрасываются на логин | Всегда `browserText` перед действием: сессия жива? |
| «Загружается…» висит 5–10 сек | `browserWait` 2–5 сек либо открыть диалог напрямую по URL с `peer_id` |
| Скриншоты обрезаются (в ВК очень много узлов DOM) | Состояние читать `browserText`/`browserEval`, скриншот — только для визуальной проверки |
| `browserText` отдаёт историю вместе с левым меню | Фильтровать по имени собеседника и времени |

## 8. Где искать человека

1. **Сначала поиск ВНУТРИ мессенджера** — он ищет по истории переписок: если человек когда-то
   писал, он находится сразу, даже с закрытым профилем.
2. **Потом глобальный поиск людей** (`/search?c[section]=people`). У закрытых профилей он может
   вернуть десятки «рекомендаций» (однофамильцы, тот же город) — это НЕ результат поиска. Нет
   нужной фамилии → считай поиск пустым и не перебирай рекомендации.
3. **Дубликаты имён** — всегда уточняй адресата (город, возраст, фото, «в друзьях»).
4. Кнопка «Написать сообщение» в результатах поиска открывает диалог сразу, минуя профиль;
   на странице профиля то же делает кнопка «Сообщение».
