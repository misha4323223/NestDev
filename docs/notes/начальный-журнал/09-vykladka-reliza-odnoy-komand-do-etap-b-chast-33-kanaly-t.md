## Выкладка релиза одной командой (1.5.175)

Канал автообновления у установленных копий — это релиз на GitHub с файлами `latest.yml` и
установщиком (`electron-updater`, `releaseType: release`). Сборка (`npm run dist:win`) выкладывать
не умеет — она идёт с `--publish never`, — а руками легко ошибиться четыре раза подряд: взять версию
из `package.json` вместо собранного `latest.yml`, забыть сам `latest.yml` в релизе (обновление просто
не найдётся), выложить поверх занятого тега (прошлый релиз уходит молча) или сделать релиз черновиком,
которого `electron-updater` не видит вовсе.

Новый `scripts/publish-release.js` (команда `npm run release:win`) делает это за человека:

- версию и имя установщика берёт **из `dist/latest.yml`**, а не из `package.json`: тег и версия внутри
  сборки обязаны совпадать;
- требует `latest.yml` в релизе и настоящий установщик на диске (без `blockmap` предупреждает — обновление
  будет качаться целиком, но работать будет);
- знает `owner/repo` из `electron-builder.yml`, а не из `origin`: репозиторий переименовывали,
  и origin может указывать на старое имя через редирект;
- не даёт выложить поверх занятого тега и подсказывает, как удалить неудачный релиз;
- текст релиза уходит **файлом** (`--notes-file`): многострочный аргумент ломается в оболочке Windows,
  где скрипт и запускается;
- печатает план до выкладки и требует подтверждения; без `--yes` и без терминала отказывается выкладывать.

Флаги: `--dry-run` (только показать), `--yes`, `--notes-file <файл>`, `--dist <папка>`.

### Живой прогон поймал мою же ошибку — и это главное в заходе

Мост к системному разделу я написал как `envPathInfo: () => envPathInfo` — то есть отдавал
модулю **саму функцию**, тогда как модуль её зовёт (`envPathInfo().value`). У функции читалось
свойство `value` (undefined), и `ycEnsurePath` звал `setMergedPath(undefined, <папка yc>)`:
**PATH процесса заменялся одной папкой yc CLI**. Команды агента теряли `rm`/`touch`/`git` и
падали с «not found» — молча, без исключения.

Ни `npm test`, ни smoke этого не видели: подмена в наборе возвращала объект (как и ждёт модуль),
а настоящий мост возвращал функцию — проверка не совпадала с реальностью. **Увидел живой прогон
раунда**: сценарий с подтверждением опасной команды проверяет, что файл после согласия создан, —
файла не было. Ровно поэтому живые прогоны в этом проекте обязательны.

Исправлено: мост отдаёт РЕЗУЛЬТАТ (`envPathInfo: () => envPathInfo()`). Сверх этого:
- отдельная проверка в наборе модуля на форму моста;
- **целевой негативный контроль** (2 из 2): с мостом, сломанным обратно, падает и набор модуля,
  и живой прогон раунда; main.js возвращается байт в байт.

Заодно поправлена слабость в живом наборе окружения: при отсутствии `printenv` в образе
(в busybox его нет) проверка «дамп секретов не показывает» проходила **на ошибке команды**, а не
на дампе. Теперь команда дампа выбирается по факту (`set` — встроенная), явный запрос делается
раскрытием переменной, и добавлено требование «дамп вообще отработал».

## Правка 1.5.178: вывод команды больше не уезжает в контекст целиком

Закрывает пункт «найдено, но не менянное» из части 23.

**Было:** ограничение `slice(0, 6000)` стояло только в ветке ОШИБКИ. Успешная команда
возвращала вывод целиком: `npm test`, сборка или `git log` на большом проекте печатали
сотни тысяч знаков, и они вытесняли переписку из контекста (обрезка истории потом резала
уже саму задачу).

**Стало:** и успех, и ошибка режут вывод **тем же правилом, что и остальные инструменты** —
`truncateText` из ядра (одна точка правды, пометка «… (обрезано: N символов)»). Молчаливо
обрезанный вывод модель читает как закончившийся на середине, поэтому пометка обязательна.

Две тонкости, каждая из которых была отдельным решением:

1. **Обрезка идёт по потокам, а не по склейке.** Если резать общий текст, длинный `stdout`
   съедает `stderr` — а ошибка сборки как раз там, и агент увидел бы только прогресс.
   Поэтому `stdout` и `stderr` режутся отдельно, по 3000 знаков каждый (предел 6000).
2. **Обрезка — до отметки времени.** «(0.4 с)» обязана остаться видимой: по ней видно,
   что команда реально работала, а не упала мгновенно.

### Контроли нашли дыры в моих проверках — это их работа

1. `canNotify`: «без Notification» проходило на **отсутствии метода `show()`** у заглушки,

   адресе шины.
2. `mk({ Notification: undefined })` не проверял ничего: стенд считал явный `undefined`
   за «не передан» и подставлял рабочий уведомитель. Теперь различается по наличию ключа.
3. Снятие проверки канала в `notifyUser` не ловилось: у заглушки не было `show()`,

4. Дела без окна: проверялось только `window: null`, а вторая половина условия
   (`isDestroyed`) — нет. Добавлено закрытое окно (свёрнуто в трей).
5. Название проверки проводки печаталось с отступом, и контроль сверял подстроку

## Этап B, часть 28.1: лечение трёх находок части 28 (1.5.184)

### 1. Секреты в свежем репозитории — это была дыра, а не шероховатость

`git restore --staged` требует HEAD. В репозитории без первого коммита страховка
`stageAllSafe` молча падала с «could not resolve HEAD», и имена вида `secrets.env` (их не
берёт исключение в самой команде) оставались в индексе — то есть могли уехать и в
авто-чекпоинт, и в первый коммит через «Изменения»/публикацию.

Команда теперь выбирается по наличию HEAD:

- **HEAD есть** → `restore --staged` (как было): правка отслеживаемого файла снимается с
  индекса, а файл остаётся в истории;
- **HEAD нет** → `rm --cached -q -f -- …`: файл уходит из индекса, на диске остаётся.

Почему нельзя просто заменить команду на `rm --cached`: проверено на настоящем git — у
файла, который УЖЕ отслеживается, `rm --cached` индексирует УДАЛЕНИЕ, и коммит стёр бы файл
из репозитория. Поэтому в наборе стоит сторож ровно на это: «отслеживаемый секрет НЕ
удаляется из репозитория» (правка снята с индекса, версия в HEAD цела), плюс «секрет, уже
закоммиченный и не изменённый, из индекса не выпадает» (страховка трогает только
подготовленное к коммиту, а не чужую историю).

### 2. Отказ git доходил сырым английским текстом — четыре канала

`runGit` на любом отказе заполняет `err`, и обычно это «Command failed: git …». Из-за этого
четыре запасных понятных текста в `git-ipc.js` (`… || "Не удалось подтянуть изменения"`,
`… || "Не удалось откатить (возможен конфликт)"`, `… || "Не удалось отменить коммит"`,
`… || "Коммит не создан (нет изменений?)"`) были **недостижимы**: человек видел английскую
строку команды.

Теперь причина разбирается (`gitFailReason`): «nothing to commit» → объяснение «коммитить
нечего» с причиной (файлы секретов в коммит не берутся); конфликт → как разрешить;
незакоммиченные правки → что сделать сначала; не git-репозиторий и «pathspec не найден» →
короткая причина. **Незнакомый отказ отдаётся как есть** — выдумывать объяснение хуже, чем
показать настоящий текст; на это есть отдельная проверка.

### 3. Аудит переноса научился бэкенд-модулям

`scripts/audit-extractions.js` собирал путь как `src/renderer/<модуль>` и на бэкенд-модуле

**Что было.** `killProcessesOnPort` на macOS/Linux брала вывод
`lsof -ti tcp:<порт> || fuser <порт>/tcp` и превращала в PID **все числа из текста**:
`(String(out).match(/\d+/g) || []).filter((x) => Number(x) > 1)`. Живая проверка части 31

**Как исправлено.**
- `parsePortOwners(out)` — построчный разбор: `lsof -ti` печатает по ОДНОМУ PID в строке
