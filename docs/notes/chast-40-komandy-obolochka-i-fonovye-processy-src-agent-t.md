## Часть 40, заход 4: команды, оболочка и фоновые процессы (src/agent-tools-run.js)

Пятнадцать обработчиков уехали из `agent-tools.js` в свой модуль: `shellsStatus`, `runCommand`,
`runCommandOutput`, `runCommandAsAdmin`, `runScript`, `startBackground`, `listBackground`,
`backgroundOutput`, `sendInput`, `stopBackground`, `shellStart`, `shellSend`, `waitUntil`,
`timeoutCommand`, `retryCommand` — 280 строк модуля. Реестр: **1831 → 1619** строк. Наружу те же
**159 имён в том же порядке** (ссылки `run.имя` на прежних местах; куски несмежные).

**Живого моста не нужно.** Ни один из пятнадцати не читает состояние прогона — всё приходит тем
же плоским `deps` (22 имени: `runTerminalCommand`, `normalizeShell`, `resolveShell`,
`shellsStatus`, `bgProcesses`, `bgSpawn`, `bgKill`, `bgTail`, `bgWaitFor`, `spawnCollect`,
`waitOutputQuiet`, `termAgentEcho`, `SERVER_CMD_RE`, `explainExit`, `runAsAdmin` и другие).
Прогон это отдельно проверяет: модуль собран РОВНО с одним аргументом.

**Сторожа — та же ловушка, четвёртый раз, и на этот раз с моей ошибкой.** Первый прогон набора
дал три падения: «shell: нет оболочки», «shellsStatus: инструмент, промпт, ядро и САММАРИ»,
«startBackground: без оболочки честная ошибка». Причина одна: сторожа ищут ТЕЛА инструментов в
склеенном доме (`backendSrc()`), а модуль в список дома не внесён. Заодно вскрылось, что
`hasTool` знает только две формы объявления (`case "имя"` и `"имя": async …`) и не знает
третьей — ссылочной. Исправлено по смыслу: (1) в три списка дома добавлены `agent-tools-write.js`
(пропущенный в заходе 3b) и `agent-tools-run.js`; (2) `hasTool` теперь признаёт и
`"имя": модуль.имя,`. Правило прежнее: сторож ищет функцию ПО ИМЕНИ во всём доме, а не по файлу.

**Новый живой прогон `scripts/live-tools-run.js` (`npm run test:live:tools-run`) — 45 ✅ / 0 ❌.**
Здесь одного «функция вызвана» мало: эти инструменты РАБОТАЮТ С ЖИВОЙ МАШИНОЙ. Прогон запускает
настоящие команды оболочки, настоящий фоновый процесс и настоящую shell-сессию:
- `shellsStatus` — оболочки ЭТОЙ машины, состояние каждой и выбор оболочки;
- `runCommand` — настоящий вывод, названный каталог, отказы (пустая команда, негодная оболочка),
  и таймаут на команде-сервере: инструмент обязан подсказать `startBackground`, а не молчать;
- фоновый процесс: id, **живой PID** (`process.kill(pid, 0)`), видимость в `listBackground`,
  вывод по маркеру, чужой id с подсказкой, остановка — и отдельно, что PID после неё **действительно
  мёртв** (иначе следующий запуск упрётся в занятый порт);
- `shellStart`/`shellSend` — сессия сохраняет состояние между командами (`PROGON_VAR=42` →
  `значение=42`), чужая сессия объяснена;
- `runCommandOutput` — сбор вывода, маркер готовности и ВЕТКА dev-сервера (`node server.js`
  уходит в фон, готовность ловится по маркеру, процесс гасится);
- `timeoutCommand` — успех, принудительная остановка по лимиту, объяснение кода возврата;
  `retryCommand` — обе попытки в ответе, объяснение кода, и что успешная команда не повторяется;
- `runScript` — настоящий скрипт из `package.json` (через настоящий npm), отсутствующий скрипт
  со списком доступных, скрипт без имени;
- `waitUntil` — ожидание настоящее (замерено по часам, 1000 мс), а не на словах;
- `runCommandAsAdmin` без прав — честный отказ про pkexec/sudo, а не тишина.

Прогон сам гасит свои процессы (в `finally` + список запущенных id), иначе следующий запуск
упёрся бы в занятый порт.

**Контроль (файл возвращён, `sha256` совпал — `383fb0c4…`).** Снятое ожидание вывода в
`shellSend` (`waitOutputQuiet`) ловят сверка переноса и живой прогон — ровно проверкой «состояние
сессии сохранилось между командами» (`(нет вывода)`). Набор не ловит и не должен: выполнять
настоящие команды в быстром юнит-наборе — значит получить плавающие падения. Для этого дома
поведенческий сторож — живой прогон, и это записано осознанно.
