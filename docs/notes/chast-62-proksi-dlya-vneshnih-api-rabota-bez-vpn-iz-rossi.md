## Часть 62: прокси для внешних API — работа без VPN из России

**Зачем.** Часть AI-API (OpenAI, Anthropic, Google, Groq) из России без VPN недоступна, а VPN на
всю машину — плохой ответ: он заворачивает и локальные обращения (свой Ollama, LM Studio, git к
своим репозиториям, внутренние сервисы), и человек теряет доступ к ним. Нужен точечный обход:
прокси ТОЛЬКО для запросов к провайдеру.

**Что сделано.** Настройки → новая вкладка «🌍 Прокси для внешних API» (`data-tab="proxy"`, полей
три: `s-proxy-enabled`, `s-proxy-url`, `s-proxy-bypass-local` плюс кнопка «🔌 Проверить»).

- Новый модуль `src/net-proxy.js` (без внешних зависимостей): `parseProxy` (адрес без схемы читается
  как http, `socks5h://` как socks5, логин/пароль раскодируются, `redactProxy` не отдаёт секрет
  наружу), `isLocalUrl` (localhost, `*.local`, 127.x, 10.x, 172.16-31.x, 192.168.x, 169.254.x, ::1),
  `proxyFor` (решение на КАЖДЫЙ запрос: галочка выключена, адрес битый, цель не http(s) или цель
  локальная при включённом `proxyBypassLocal` → `null` = обычный fetch), `fetchFor` и `testProxy`.
- Умеет и http(s)-прокси (для http-цели — запрос в абсолютной форме, для https — тоннель CONNECT),
  и SOCKS5/SOCKS5h по RFC 1928+1929. Имя узла уходит прокси как домен (`ATYP 0x03`) — это главное:
  часть API недоступна именно по DNS/SNI, а не только по IP.
- Ответ отдаётся в форме fetch (`ok/status/statusText/headers.get/body/text/json/arrayBuffer`) —
  транспорт провайдера и раунд читают его тем же кодом, что и обычный ответ. 3xx прокси-запрос
  проходит сам (`MAX_REDIRECTS = 4`, 301/302/303 на POST превращаются в GET, как в браузере).
- **Грабли, которые стоит помнить.** Готовое соединение нельзя отдать Node через `agent: false` +
  `createConnection` — при `agent: false` Node создаёт свой агент и `createConnection` НЕ зовёт:
  запрос уходил бы напрямую к цели, мимо прокси (поймано стендом, потом добавлена проверка).
  Поэтому на каждый запрос собирается свой одноразовый агент (`oneShotAgent`, `keepAlive: false`) с
  подменённым `createConnection`. Без теста это тихо «работало бы» и не проксировало.
- Одна точка подстановки: `src/renderer/provider-config.js` получил `setFetchImpl` + `netFetch`, а
  `src/main.js` при сборке ставит туда `(url, opts) => netProxy.fetchFor(loadSettings(), url, opts)`.
  На `netFetch` переведены транспорт (`provider-transport.js`), окно контекста (`context-window.js`)
  и картинки (`image-tools.js`) — раньше каждый звал `fetch` сам. В браузере (веб-превью) подстановки
  нет, и `netFetch` просто зовёт обычный fetch: поведение прежнее.
- Раунд прогона: `netProxy` уходит в `createRunAi` → `createRunRound`, а `src/run-round.js` строит
  `providerFetch` (нет модуля — обычный fetch), поэтому настройка не может уронить старую сборку.
- Проверка связи — из ГЛАВНОГО процесса, канал `settings:testProxy` (`src/net-proxy-ipc.js`, через
  `ipcGuard`, права как у настроек): идёт тем же кодом, что поведёт настоящий запрос агента, делает
  реальный запрос наружу и показывает выходной IP (`api.ipify.org` → `ifconfig.me`, либо свой
  `testUrl` для теста). Проверка из окна говорила бы о ДРУГОМ соединении (у Chromium свой стек).
- Локальные адреса и выключенная настройка = байт в байт прежнее поведение: свой Ollama проксирован
  не будет никогда.

**Найдено живым прогоном и починено (часть 59).** `src/main.js` передавал в `createRunAi`
имя `roleMismatchNote`, а в разборе `agent-core.js` его НЕ было: это `ReferenceError` в момент
загрузки оболочки, то есть приложение вообще не стартовало (сторожа этого не видели — они
читают текст, а не запускают оболочку). Имя добавлено в разбор. Живой прогон ниже теперь
грузит `main.js` по-настоящему и такое ловит сразу.

**Живой прогон** `scripts/live-proxy.js` (`npm run test:live:proxy`) — настоящий `main.js`
без окна Electron, между прогоном и подменённым провайдером стоит НАСТОЯЩИЙ http-прокси,
который записывает всё, что через него прошло (22 проверки): прокси включён и локальные
адреса не исключены → ВСЕ запросы (и чат, и вспомогательные — окно модели) идут через
прокси; цель локальная → мимо прокси; прокси выключен → мимо прокси; канал проверки
прокси из окна отвечает словами на мусор и на пустой адрес. Негативные контроли:
`--break=proxy` (раунд снова голый fetch) — 3 красных, `--break=renderer` (гнездо
`setFetchImpl` обнулено, вспомогательные запросы мимо прокси) — 1 красный, `--break=bypass`
(исключение локальных адресов убрано) — 1 красный; файлы восстанавливаются байт в байт.
Протокол SOCKS5 живьём проверяет набор (там настоящий SOCKS5-сервер с логином и паролем),
а живой прогон — путь «прогон → транспорт → прокси». Наружу в интернет ни набор, ни прогон
не ходят: настоящую связь с внешним API проверяет человек кнопкой «Проверить».

**Проверки.** Новый набор `test/net-proxy.test.js` (11 проверок, в цепочке `npm test`; 79 наборов).
Он поднимает НАСТОЯЩИЕ прокси и цель на 127.0.0.1 и проверяет обе ветки живьём: http-прокси
(абсолютная форма и тоннель CONNECT), SOCKS5 с логином/паролем и без, отказ 407 с понятным текстом,
проверку связи с выходным IP, схему настроек и всю проводку (main → прогон → окно → гнездо
провайдера → разметка/панель). TLS подменяется простым сокетом (`createNetProxy({ tls })`):
проверяется своя логика тоннеля, а не сертификаты. `test/smoke.test.js`: модули `net-proxy.js` и
`net-proxy-ipc.js` добавлены в `backendSrc()` и оба списка `scanWiring`, вкладок 10 → 11, и
подправлена проверка картинок (`fetch` → `callApi`) — старая ловила голый fetch.
Проверку прокси наружу (настоящий внешний API) остаётся за человеком — ровно для этого и
сделана кнопка «Проверить»; ни набор, ни живой прогон в интернет не ходят.
Версия 1.5.220 (набор 1.5.226) не менялась.
