устройства. Стало: сервер на `https` с самоподписанным сертификатом, адрес в QR-коде
и в списке адресов — `https://…`, а телефон строит канал как `wss://` из схемы
страницы (это уже умел `mobile-api.js` — менять его не пришлось).

Сертификат собирается **чистым Node, без новых зависимостей**: ASN.1/DER вручную
(X.509 v3: basicConstraints CA+pathLen 0, keyUsage, extendedKeyUsage serverAuth,
subjectAltName с адресами ПК и именами, subjectKeyIdentifier), подпись — SHA-256 с
ключом RSA 2048. Ключ и сертификат лежат в `userData/bridge-tls`, ключ — с правами
600. Пересоздаются, когда: сертификата/ключа нет, подпись не сходится, он битый,
срок меньше 30 дней, **сменились адреса ПК** (старый сертификат на новый адрес уже не
годится — это самый частый случай после переезда к другой точке доступа).

Решения, которые стоит помнить:

- **Сбой сертификата не выключает мобильный доступ.** Мост падает обратно на http,
  а причина уходит в статус (`mobile:status.tls`/`tlsError`) и в панель настроек:
  «⚠ Мост работает без шифрования: …». Лучше доступ с честным предупреждением, чем
  недоступное приложение.
- **Выключателя шифрования в настройках нет и быть не должно.** Телефон умеет писать
  настройки, поэтому галочка «без TLS» стала бы кнопкой «снять защиту» для того, кто
  уже в сети. Аварийный путь — только сбой выпуска сертификата.
- **Панель говорит про предупреждение браузера телефона.** Сертификат самоподписанный:
  первый вход — «Дополнительно» → «Перейти на сайт». Без этой строки человек решает,
  что подключение сломано. Проверяются оба состояния строго по значению поля: если
  главный процесс про TLS ничего не сказал (старый мост), панель не выдумывает ни
  «зашифровано», ни «открыто».

Проверки: `test/bridge-tls.test.js` — разбор сертификата штатным
`crypto.X509Certificate`, сверка подписи с самим собой, SAN (checkIP/checkHost),
переиспользование и пересоздание (битый, истёкший, сменился адрес), **настоящее
рукопожатие**: с сертификатом как доверенным корнем — `authorized: true`, без него —
отказ `SELF_SIGNED`; мост отдаёт страницу по https, а канал поднимается рукопожатием
WebSocket поверх TLS. Живой прогон `test:live:mobile` теперь ходит по `wss` и
отдельно проверяет рукопожатие с доверенным корнем на живом мосте.

Честные оговорки: (1) сертификат самоподписанный — телефон один раз показывает
предупреждение, которое можно принять не глядя; это осознанный размен, полноценный
сертификат требует домена; (2) установка PWA на телефоне при ошибке сертификата может
не сработать (service worker регистрируется «best effort», интерфейс от этого не
зависит); (3) адрес берётся из сертификата, поэтому при смене сети телефон увидит
новый сертификат и попросит подтверждение заново — это ожидаемо и записано в meta.json
(поле `reason`).

### 2. OTA-набор подписывается, и приложение это проверяет (`src/ota-sign.js`)

Было: целостность набора держалась на sha256 из манифеста, а манифест лежит РЯДОМ с
набором. Кто положил в папку поддельный `bundle.json`, тот положит и свой манифест с
его хешем — и проверка сходится. Набор при этом исполняется в приложении.

Стало: манифест несёт `sig` (подпись строки `bundle.json` — тех же байтов, из которых
считается sha256) и `keyId` (отпечаток открытого ключа, 16 hex). Приложение проверяет
подпись **до распаковки**, порядок такой: sha256 → подпись → распаковка → синтаксис →
своп папок. Ключ Ed25519 (короткая подпись, быстрая проверка, всё в `crypto`).

Расклад с ключами:

- `src/ota-trust.js` — список доверенных ОТКРЫТЫХ ключей. **Пустой список = подпись не
  настроена**: наборы принимаются без неё (иначе приложение осталось бы без обновлений
  вовсе), а панель «Обновление кода» говорит об этом прямым текстом и подсказывает
  команду. Как только в списке появляется ключ, принимаются ТОЛЬКО наборы, подписанные
  им.
- `npm run ota:key` — создаёт ключ у владельца (`~/.ai-agent-ota-key.pem`, права 600;
  в репозиторий не попадает никогда). `-- --trust` вписывает открытую часть в
  `src/ota-trust.js` читаемым блоком (шаблонные строки, чтобы файл можно было смотреть
  глазами). Повторный запуск не плодит дубликаты.
- `scripts/make-ota.js` — подписывает набор и печатает, доверен ли ключ. Без ключа
  сборка останавливается: молча выпустить неподписанный набор — это тихо понизить
  защиту. Для осознанного случая есть `--unsigned`.
- Переменные для стендов: `AI_AGENT_OTA_TRUST` (путь к файлу с ключами или сам PEM),
  `AI_AGENT_OTA_TRUST_FILE` (куда писать список — проверки вносят ключ в копию, а не в
  репозиторий), `AI_AGENT_OTA_ALLOW_UNSIGNED=1` (послабление только для разработки).

Отказы объясняются человеку, а не «не удалось»: «Набор не подписан — обновление
отклонено. Подпишите набор своим ключом…», «Набор подписан неизвестным ключом <id> —
доверенные: <список>», «Подпись набора не сходится — файл изменён после сборки».
Применённый набор помнит ключ (`version.json.keyId`), статус отдаёт и его, и состояние
списка доверия (`status().trust`, `bundleKeyId`).

Проверки: `test/ota-sign.test.js` (12) и правка `test/smoke.test.js` — там наборы
теперь собираются ПОДПИСАННЫМИ стендовым ключом, доверие выдаётся переменной
окружения, то есть проверяется настоящий путь, а не послабление. Отдельно проверяется
сама атака: подменить `bundle.json` и пересчитать хеш в манифесте — подпись не сойдётся.
И отдельная проверка, что закрытый ключ не может попасть в репозиторий (в файл
доверенных уезжает только открытая часть; права 600).

### Что осталось за владельцем

- **Создать ключ подписи**: `npm run ota:key -- --trust` — одна команда, закрытая часть
  остаётся на его ПК. Пока этого не сделано, наборы принимаются без подписи, и панель
  обновления предупреждает.
- **Бандл в репозитории пока без подписи** (`--unsigned`, список ключей пуст). После
  создания ключа набор надо пересобрать: `npm run ota:bundle -- --version 1.5.192`.
- Кодовая подпись установщика Windows и подпись самого установщика — отдельная работа,
  без сертификата подписи кода она невозможна (люди увидят «неизвестного издателя»).
