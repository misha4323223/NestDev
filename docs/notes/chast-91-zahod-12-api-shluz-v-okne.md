## Часть 91, заход 12: API-шлюз в окне — создать ИЗ спецификации, посмотреть, поправить и удалить

Разрыв, который закрывает заход, был «полкой со шлюзом, но без работы с ним»:
сервис «API-шлюз» стоял на полке панели и показывал список шлюзов, а создать шлюз
ИЗ OpenAPI-спецификации, посмотреть её, поправить и удалить можно было только в
консоли облака. Между тем шлюз — это «вход» в приложение: он принимает запросы
по адресу `<id>.apigw.yandexcloud.net`, разбирает их по спецификации и уводит в
интеграции (dummy, cloud-functions, container, object-storage). Без шлюза функция
или контейнер отвечают только по своему «неудобному» адресу, а собрать сайт с
маршрутами не из чего — то есть заход развязывает руки уже сделанным
возможностям.

**Шлюз ЦЕЛИКОМ задаётся спецификацией.** Это текст OpenAPI (`openapiSpec`), JSON
или YAML: создание без него бессмысленно (облако примет пустой ресурс, который
нечего обслуживать). Поэтому пустую или не-OpenAPI спецификацию модуль отвергает
ДО сети — «это не похоже на OpenAPI» понятнее, чем отказ сервиса после операции.
Разбор спецификации лёг в модуль без зависимостей: YAML-парсер тянуть нельзя
(OTA возит только свой код), поэтому пути ищутся строками-шаблонами, а JSON
разбирается штатным `JSON.parse`. И «показать спецификацию» — ОТДЕЛЬНОЕ действие:
источников у шлюза нет отдельным полем, всё живёт в тексте (интеграции
`x-yc-apigateway-integration`).

**Изменяющие методы возвращают OPERATION — их надо дождаться.** Создание, правка
и удаление шлюза отвечают не объектом, а операцией, и её результат ждёт
`waitOperation` из `src/yandex-cloud.js`; готовый шлюз приходит в `response`
операции, а id готового читается ещё и ПЕРЕЧИТЫВАНИЕМ (как у остальных ресурсов).

**Формы честные, и это видно в коде.** Имя проверяется по правилу облака
(`[a-z]([-a-z0-9]{0,61}[a-z0-9])?`) ДО сети. Правка уходит МАСКОЙ полей
(`updateMask`): без неё облако сбросило бы неназванное в значение по умолчанию, а
с ней пустое поле значит «не меняется». Имя поля спецификации в маске —
`openapi_spec` (змеиный регистр, как требует field-mask), а в теле JSON —
`openapiSpec`; время выполнения человек пишет секундами, а модуль переводит их в
длительность (`\"5s\"`). Поиск шлюза — по имени, id ИЛИ адресу: человек называет
его по-разному. Удаление необратимо (адрес перестаёт отвечать) — оно помечено
`danger` и спрашивается ДВАЖДЫ: окном (`askConfirm` до запроса) и каналом
(`a.confirmed !== true`), потому что канал зовут не только кнопкой.

**Четыре слоя.** Модуль — новый `src/yc-apigw.js` (`listGateways`, `getGateway`,
`getSpec`, `createGateway`, `updateGateway`, `deleteGateway` плюс мелочи
`checkName`, `checkSpec`, `durationOf`, `statusHuman`, `gatewayInfo`,
`gatewayLine`, `specBrief`, `specPaths`, `matchGateway` и шаблон `SPEC_TEMPLATE`);
чистый, как REST-часть `yc-logs.js` — сеть через встроенный `fetch`, можно
подменить `fetchImpl`, поэтому он проверяется без настоящего облака. Инструмент
— `ycApiGw` (`action: list`, `gateway`, `spec`, `create`, `update`, `delete`),
сверка действия без учёта регистра, создание ДО поиска (у нового шлюза нет записи
в каталоге), изменяющие действия под разрешениями облака
(`allowCreate`/`allowUpdate`/`allowDelete`). Канал — `yc:apigw` в `src/yc-ipc.js`
(38-й канал моста, шесть действий), мост окна — `ycApiGw` в `src/preload.js`,
оболочка собирает ОДИН экземпляр модуля (`src/main.js`) на окно и агента.
Интерфейс — семейство `apiGateway` в `src/renderer/yc-actions.js` (плитка
«API-шлюз» уже была — у неё появилась кнопка «⚙ Действия»): специальная форма с
многострочным полем спецификации, отдельная правка-маска и опасное удаление.
Действия человека галочек агента не спрашивают — те ограничивают модель.
