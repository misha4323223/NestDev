## Часть 50: база YDB — таблицы и записи (инструмент ycDb)

**Задача (просьба человека).** Продолжение темы «облако руками агента»: сервис
Managed YDB в списке был и базу можно было СОЗДАТЬ (`ycCreate { service: "ydb" }`),
а работать с ней — нечем: ни таблиц, ни одной записи не видели ни агент, ни консоль
облака. Serverless-база создаётся ровно ради данных — то есть это пустая полка того
же рода, что секрет Lockbox без версии (часть 46) и бакет Object Storage без файлов
(часть 47).

**Другой протокол, а не другой сервис.** Таблицы живут в HTTP Document API YDB. У
него та же авторизация (IAM-токен), но протокол Amazon DynamoDB-совместимый, и это
две строгости, которые легко потерять при правке:

1. **Операция — заголовком, а не путём.** `X-Amz-Target: DynamoDB_20120810.<Метод>`,
   тело — JSON (`Content-Type: application/x-amz-json-1.0`); запрос всегда идёт в
   КОРЕНЬ адреса базы — REST-путей вида `/tables` у него нет.
2. **Значения типизированы.** Строка — `{ "S": "cat" }`, число — `{ "N": "10.5" }`,
   а не как в обычном JSON. Агент передаёт привычные значения, а обёртку ставит
   приложение (`toAttrValue`/`fromAttrValue`).

**Адрес берётся у базы.** `documentApiEndpoint` — поле самой базы (у serverless и
выделенных баз хосты разные), поэтому по памяти он не собирается. Если список отдал
краткую форму, адрес выводится из gRPC-эндпоинта: `ydb.` → `docapi.`, путь
`/<регион>/<облако>/<база>` тот же. Этому посвящён отдельный негативный контроль.

**Что сделано.** Новый модуль `src/yc-db.js` (`createYcDb`) — чистый слой Document
API (сеть и IAM приходят deps, как у `createYcService` и `createYcCosts`), и
инструмент агента `ycDb` в `src/agent-tools-cloud.js` (дом облака 13 → **14**):
`tables` (что есть), `create` (ключ: первый HASH, остальные RANGE), `describe`
(структура и число записей), `put` (запись полями), `get` (одна по ключу),
`scan` (обход, до 100), `delete` (запись по ключу), `drop` (таблица вместе с
записями — необратимо). `database` — имя или id; без него работает, только если
база в каталоге одна. `create`/`put` требуют «Разрешить агенту создавать ресурсы»,
`delete`/`drop` — «…удалять ресурсы», и запрет стоит ДО всякой сети.

**Проводка.** Реестр инструментов получает `ycDb` сам — он собран спредом
`...createCloudTools(deps)` (main.js не тронут: `yandexCloud` уже в deps, а
`ycDbApi` собирается из его же помощников). Списки имён, схемы, правила промпта,
права (`cloud.read`), справочник `yc.md` и сторож smoke знают инструмент.

**Проверки.** Новый набор `test/yc-db.test.js` — **20**, в цепочке `npm test`
(75 наборов, 0 падений). Он поднимает НАСТОЯЩИЙ HTTP-сервер Document API (операция
в заголовке, типизированные значения, отказ вида `__type`) и прогоняет через него
и слой `createYcDb`, и инструмент агента: адрес у базы / вывод из gRPC, разбор и
сборка значений, реальные запросы, полный цикл записи, отказы словами, разрешения.

**Находка в сторожах (не в коде).** `clipboard-tools.test.js` собирает
`createCloudTools` с deps БЕЗ `yandexCloud` (буферу обмена облако не нужно) — и
падал на сборке `ycDbApi`. Сборка стала защитной (`const ycApi = yandexCloud || {}`):
стенду, которому облако не нужно, незачем требовать его ради соседнего обработчика.

**Вторая находка — сторож держал ВИД, а не смысл.** В `smoke.test.js` проверка
границы роутера требовала, чтобы браузерная группа влезала в окно ровно 22 000 —
число подобрано под длину промпта. Добавление одной строки в промпт (новый
инструмент) сдвинуло порог, и сторож покраснел на ВЕРНОЙ правке — ровно болезнь
части 49. Переписан на смысл: окно подбирается от РЕАЛЬНЫХ весов, а жёсткий резерв
истории 12 000 всё равно ловится (тогда группа не влезает и в потолок).

**Прогон.** `npm test` — exit 0 (75 наборов; smoke — 534). Живой прогон
`test:live:tools-cloud` — **87 ✅ / 0 ❌** (без регрессии; сам ycDb проверен набором
через настоящий HTTP-протокол).
